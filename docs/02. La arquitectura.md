# 02. Arquitectura de ALESSIA

## Introducción

ALESSIA fue desarrollada utilizando una arquitectura **Retrieval-Augmented Generation (RAG)**, un enfoque que combina la capacidad de comprensión y generación de texto de los modelos de lenguaje con una base de conocimiento compuesta por documentación oficial.

A diferencia de un chatbot tradicional, que responde únicamente utilizando el conocimiento adquirido durante el entrenamiento del modelo, una arquitectura RAG recupera información relevante desde una base documental antes de generar la respuesta. Esto permite ofrecer respuestas contextualizadas, reducir el riesgo de alucinaciones y mantener un mayor grado de fidelidad respecto de las fuentes consultadas.

---

## Objetivos de la arquitectura

La arquitectura de ALESSIA fue diseñada considerando los siguientes principios:

* Separación clara de responsabilidades entre cada componente.  
* Modularidad para facilitar el mantenimiento y la evolución del proyecto.  
* Uso exclusivo de documentación oficial como fuente de conocimiento.  
* Escalabilidad para incorporar nuevos documentos y funcionalidades.  
* Trazabilidad durante todo el flujo de procesamiento.

## Componentes de la arquitectura

### 1. Ingesta de documentos

La primera etapa consiste en incorporar documentos oficiales al sistema.

Actualmente ALESSIA trabaja con documentos en formato PDF, los cuales son procesados para extraer su contenido textual y la información necesaria para su posterior utilización.

Durante esta etapa también se generan identificadores que permiten mantener la trazabilidad de cada documento durante todo el flujo del sistema.

---

### 2. Procesamiento

Una vez cargados, los documentos son sometidos a un proceso de limpieza y normalización.

Posteriormente, cada documento es dividido en fragmentos (chunks), permitiendo que la búsqueda semántica opere sobre unidades de información más pequeñas y relevantes.

Cada fragmento mantiene su relación con el documento de origen mediante identificadores únicos y metadatos asociados.

---

### 3. Generación de embeddings

Cada fragmento es transformado en un vector numérico mediante un modelo de embeddings.

Estos vectores representan el significado semántico del texto y permiten comparar consultas utilizando similitud semántica en lugar de coincidencias exactas de palabras.

---

### 4. Base de datos vectorial

Los embeddings son almacenados en una colección de ChromaDB.

Esta base de datos permite recuperar rápidamente los fragmentos más similares a una consulta realizada por el usuario.

La utilización de una base vectorial desacopla el almacenamiento del proceso de generación de respuestas y facilita la escalabilidad del sistema.

---

### 5. Recuperación de información (Retriever)

Cuando el usuario realiza una consulta, esta también es transformada en un embedding.

Posteriormente se realiza una búsqueda por similitud dentro de la base vectorial para recuperar los fragmentos más relevantes.

Esta etapa constituye el primer filtro de información.

---

### 6. Reordenamiento (Reranker)

Los fragmentos recuperados son evaluados nuevamente mediante un modelo Cross Encoder.

A diferencia de la búsqueda vectorial, el reranker analiza simultáneamente la consulta y cada fragmento, permitiendo obtener un orden de relevancia más preciso.

El resultado es un conjunto reducido de fragmentos altamente relacionados con la pregunta del usuario.

---

### 7. Construcción del prompt

Los fragmentos seleccionados son incorporados al contexto enviado al modelo de lenguaje.

Además del contexto documental, el prompt incluye instrucciones específicas que definen el comportamiento esperado de ALESSIA, entre ellas:

* responder únicamente utilizando la información proporcionada;  
* indicar cuando no existe información suficiente;  
* mantener un lenguaje claro y comprensible;  
* priorizar información oficial.

Esta etapa permite controlar el comportamiento del modelo y reducir respuestas fuera del dominio del proyecto.

---

### 8. Generación de la respuesta

El prompt es enviado al modelo de lenguaje a través de OpenRouter.

El modelo utiliza el contexto proporcionado para generar una respuesta coherente y alineada con la información recuperada.

La responsabilidad del modelo no es aportar conocimiento adicional, sino sintetizar y comunicar la información disponible en la documentación oficial.

## Organización del proyecto

La implementación sigue una estructura modular, donde cada componente posee una responsabilidad claramente definida.

src/

├── ingestion/  
│   ├── cleaner.py  
│   └── loaders.py  
│  
├── models/  
│   ├── chunk.py  
│   └── document.py  
│  
└── processing/  
    ├── chunker.py  
    ├── vector\_store.py  
    ├── retriever.py  
    ├── reranker.py  
    ├── prompt\_builder.py  
    ├── llm\_client.py  
    └── generation.py

Esta organización favorece la reutilización del código, facilita las pruebas unitarias y permite modificar componentes individuales sin afectar el resto del sistema.

---

## Principios arquitectónicos

Durante el desarrollo de ALESSIA se adoptaron los siguientes principios de arquitectura:

* **Responsabilidad única:** cada módulo realiza una tarea específica.  
* **Bajo acoplamiento:** los componentes interactúan mediante interfaces simples.  
* **Alta cohesión:** cada módulo concentra funciones relacionadas.  
* **Escalabilidad:** la arquitectura permite incorporar nuevas fuentes documentales y modelos.  
* **Mantenibilidad:** el código fue organizado para facilitar futuras modificaciones.  
* **Trazabilidad:** los documentos y fragmentos mantienen identificadores únicos durante todo el pipeline.

---

## Consideraciones finales

La arquitectura de ALESSIA fue diseñada priorizando la claridad, la modularidad y la evolución del proyecto.

Aunque esta primera versión está enfocada en documentación oficial relacionada con la gestión del riesgo de desastres para la comuna de Valdivia, la arquitectura es lo suficientemente flexible para incorporar nuevas fuentes de información, otros dominios de conocimiento y futuras funcionalidades sin requerir cambios estructurales significativos.

Este enfoque permite que ALESSIA evolucione de manera incremental, manteniendo una base técnica sólida y alineada con buenas prácticas de ingeniería de software.
