# 04\. Estrategia de pruebas

## Introducción

La estrategia de pruebas de ALESSIA fue diseñada para validar el comportamiento del sistema en distintos niveles, asegurando que cada componente cumpliera su responsabilidad antes de integrarse al resto de la arquitectura.

Más que buscar una cobertura artificialmente alta, el objetivo fue verificar que las funcionalidades críticas del proyecto respondieran correctamente ante escenarios representativos del uso real.

Las pruebas acompañaron el desarrollo desde las primeras etapas del proyecto y formaron parte del proceso de construcción de cada módulo.

---

# Objetivos

La estrategia de pruebas tuvo como principales objetivos:

* Validar el comportamiento esperado de cada componente.  
* Detectar errores de forma temprana durante el desarrollo.  
* Reducir el riesgo de regresiones al incorporar nuevas funcionalidades.  
* Facilitar futuras refactorizaciones.  
* Aumentar la confiabilidad del sistema.

---

# Niveles de prueba

ALESSIA fue validada mediante distintos niveles de pruebas, cada uno con un propósito específico.

## Pruebas unitarias

Las pruebas unitarias verifican el comportamiento de componentes individuales de manera aislada.

Durante el desarrollo se implementaron pruebas para los módulos fundamentales del sistema, incluyendo:

* modelos de datos;  
* carga de documentos;  
* limpieza de documentos;  
* generación de fragmentos (chunking).

Estas pruebas permitieron comprobar que cada módulo produjera los resultados esperados de forma independiente.

---

## Pruebas de integración

Las pruebas de integración verifican la correcta interacción entre componentes que, individualmente, ya habían sido validados.

En ALESSIA este nivel permitió comprobar el funcionamiento conjunto de etapas como:

* procesamiento de documentos;  
* generación de embeddings;  
* almacenamiento vectorial;  
* recuperación de información;  
* reranking;  
* generación de respuestas.

El objetivo fue asegurar que el flujo completo funcionara correctamente cuando los distintos módulos trabajaban de forma coordinada.

---

## Pruebas funcionales

Las pruebas funcionales permitieron validar que el sistema respondiera correctamente desde la perspectiva del usuario.

Estas pruebas incluyeron consultas representativas utilizando documentación oficial incorporada a la base de conocimiento.

Durante esta etapa se verificó que:

* las respuestas fueran coherentes con la consulta realizada;  
* la información proviniera del contexto recuperado;  
* el modelo respetara las instrucciones definidas en el prompt;  
* el sistema indicara cuando no existía información suficiente para responder.

---

## Prueba End-to-End

Finalmente se realizó una validación completa del sistema utilizando el flujo real de ejecución.

Esta prueba consideró todas las etapas de la arquitectura:

1. procesamiento documental;  
2. generación de embeddings;  
3. recuperación de información;  
4. reranking;  
5. construcción del prompt;  
6. generación de la respuesta final.

El objetivo fue comprobar que todos los componentes interactuaran correctamente en un escenario equivalente al uso real de la aplicación.

---

# Casos de prueba

Las pruebas se diseñaron utilizando preguntas representativas del dominio de la gestión del riesgo de desastres.

Entre los aspectos evaluados se consideraron:

* recuperación de información relevante;  
* consultas fuera del dominio del proyecto;  
* ausencia de información suficiente;  
* coherencia entre la respuesta y la documentación utilizada;  
* comportamiento general del sistema frente a distintas formulaciones de una misma consulta.

---

# Herramientas utilizadas

Durante el desarrollo se utilizaron distintas herramientas para validar el comportamiento del proyecto.

Entre ellas:

* **pytest** para las pruebas unitarias;  
* **Jupyter Notebook** para pruebas exploratorias y validación incremental;  
* **Streamlit** para validar la experiencia de usuario en un entorno de ejecución completo.

Cada herramienta cumplió un rol específico dentro del proceso de aseguramiento de la calidad.

---

# Filosofía de pruebas

Uno de los principios adoptados durante el desarrollo fue priorizar pruebas que validaran comportamiento, evitando generar pruebas cuyo único objetivo fuera aumentar métricas de cobertura.

Las pruebas fueron diseñadas para responder preguntas como:

* ¿El módulo cumple correctamente su responsabilidad?  
* ¿Produce el resultado esperado?  
* ¿Se comporta correctamente frente a distintos escenarios?  
* ¿Puede modificarse el código con confianza sin romper funcionalidades existentes?

Este enfoque permitió mantener una estrategia de pruebas práctica, útil y alineada con las necesidades reales del proyecto.

---

# Resultados

La estrategia de pruebas permitió detectar y corregir distintos problemas durante el desarrollo, especialmente en la interacción entre módulos del pipeline RAG.

Las validaciones realizadas contribuyeron a mejorar la estabilidad del sistema antes de cada integración y facilitaron la evolución incremental del proyecto.

Además, el uso continuo de pruebas permitió realizar refactorizaciones con mayor seguridad, manteniendo el comportamiento esperado de los componentes ya implementados.

---

# Consideraciones finales

La calidad de un sistema basado en Inteligencia Artificial no depende únicamente del modelo utilizado, sino también de la confiabilidad de todo el pipeline que lo rodea.

Por esta razón, las pruebas fueron consideradas un componente esencial del desarrollo de ALESSIA y no una actividad realizada al finalizar la implementación.

Esta estrategia permitió construir una primera versión robusta, validada en distintos niveles y preparada para evolucionar mediante nuevas funcionalidades sin comprometer la estabilidad del proyecto.
